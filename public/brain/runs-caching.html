Runs, analytics & caching

Run log (runLog.ts)

  • Written by allowlist — ids, statuses, timings, counts, condition traces — never by dumping the run object. This is contact-enrichment traffic; logging everything by default would turn a credentials product into a PII store.
  • The caller's input is stored (capped at 4KB) so a row is recognisable. The result is not stored unless the endpoint opts into "Save request and response bodies".
  • One batched transaction (header + step rows) inside after() — costs the caller nothing, and a failed log can never turn a successful run into an error.
  • Test runs are deliberately never logged.

Analytics (runAnalytics.ts, Runs tab)

The two-rates framing is deliberate and must not be collapsed into one column. A later step in a waterfall only sees the cases everything before it missed, so raw success rates aren't comparable between steps.
  • Hit rate — of the runs where the step actually ran. For watching one provider over time.
  • Share of answers — of every run that got an answer. The "what would I lose by dropping it" number.
  • Cost per answer — the number that decides whether a vendor stays.
  • hit_rate is null when a step never ran — "no data" and "0%" are opposite conclusions and must not render identically.
  • Step names in analytics come from the run rows (name at the time), so a renamed step doesn't rewrite its own history.

Caching (runCache.ts, engine/cacheKey.ts)

  • Cache key = SHA-256 over owner + endpoint + version + canonicalized input.
  • Owner in the key: one tenant's enriched contact can never be served to another.
  • Version in the key is the invalidation story: edit a step, every old answer goes cold, nothing to remember to purge. Verified live.
  • Canonicalization: key-order independent; strings trimmed + lowercased by default (cache_key_normalize); include/exclude field lists; array order still matters.
  • Only success and partial cached. A miss is not — vendors keep adding data, "nobody had it yesterday" shouldn't stop you asking today. An error is not — it's transient.
  • Manual purge on Settings is for the case versioning can't cover: the provider's data changed and the definition didn't.
  • Measured: cache hit = 0 upstream calls, 209ms vs 1147ms cold.

Rate limiting (consumeEndpointRate)

Per endpoint key, counted in the database with an atomic upsert per minute window — not the in-memory limiter, which is per-instance and keyed on a spoofable x-forwarded-for. Fine for a dashboard button; useless when every request buys upstream calls. 429s carry Retry-After. Verified: limit 2 → third call 429.

Retention (/api/cron/prune)

  • Daily at 04:00 via vercel.json. Deletes runs older than each endpoint's own log_retention_days (default 30), expired cache rows, stale rate counters. Step rows cascade.
  • Gated fail-closed on CRON_SECRET (constant-time compare): with no secret set it rejects everything — an open deletion endpoint would be worse than a cron that doesn't run. Secret is set on the Vercel project.
  • Verified: a backdated run and its step rows were removed; nothing else was.

Version history

Settings lists the last 20 versions with restore. Restore writes the old definition forward as a new version — append-only history, run-log references stay valid, and undoing a restore is just another restore.
