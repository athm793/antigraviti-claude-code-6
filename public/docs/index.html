1 · Setting up the proxy

A provider is one upstream API plus a pool of API keys. KeyProxy forwards your calls with the next active key injected; when a key hits a rate limit, it's benched and the next one is used automatically.

  1. Create a provider (Providers → New provider):
    FieldWhat to enter
    Target base URLThe API's origin, e.g. https://api.hunter.io. Must be publicly reachable — localhost and private ranges are refused.
    Auth header name + prefixHow this API expects its key, e.g. Authorization + Bearer , or X-Api-Key with no prefix. Check the provider's docs.
    Rate-limit status codesWhich responses mean "this key is spent" — usually 429. Only 400–599 are accepted.
    CooldownMinutes before a rate-limited key is retried. 0 = benched until you reset it.
  2. Add keys — paste them on the provider page, one per line.
  3. Call the proxy — replace the API's base URL with your proxy URL: 
    # Before — direct, one key, dies on rate limits
curl https://api.hunter.io/v2/email-finder?domain=acme.com \
  -H "X-Api-Key: real-key"

# After — through KeyProxy, rotates across the whole pool
curl https://<your-keyproxy>/api/proxy/<CONFIG_ID>/v2/email-finder?domain=acme.com \
  -H "x-master-key: <MASTER_KEY>"
    The master key (shown on the provider card) authenticates you to KeyProxy; it can also go in Authorization: Bearer …. KeyProxy strips it, injects the next pool key, and forwards everything else — method, headers, body — unchanged.

2 · Waterfalls

An endpoint is one public URL that runs an ordered list of steps. Each step calls one of your providers; rules decide whether a step runs and whether its response counts as an answer. The classic use: try Prospeo, and if it returns no email try BetterEnrich, then Hunter — one URL, one response shape, whichever provider had it.

Concepts

  • Inputs — what callers send (domain, first_name…). Each becomes a {{input.…}} token usable in any step.
  • Steps — a request template against one provider, plus an output map that pulls fields out of its response into your normalized result. Auth is never in a step — it comes from the provider's key pool.
  • Answered? — by default, a step counts as an answer when it returns 2xx and fills every required output field. So a provider replying 200 {"email": null} is a miss and the waterfall moves on. Custom conditions can demand more (e.g. score ≥ 70).
  • Stop or continue — "stop on success" makes a waterfall; "continue" makes a chain that gathers fields from several providers (e.g. find an email, then verify it).
  • Parallel groups — opt-in: consecutive steps can run at the same time. Faster, but you pay every member on every run. Results always merge in listed order, so runs are reproducible.

Building one

  1. Endpoints → New endpoint. You get the public URL and an endpoint key (shown once — it's stored as a hash).
  2. On the Build tab, declare inputs and add a step per provider, in the order you want them tried. The step editor covers conditions, output mapping, and what to do on success/failure. Or write JSON directly — see section 3.
  3. Run test executes the unsaved draft against your real providers (live calls, real credits, nothing logged) and shows exactly what each step did, including why a condition passed or failed.
  4. Save waterfall. Every save is a version; Settings has the history and one-click restore.

Worth knowing

  • Caching (Settings) — a repeated lookup returns the answer you already bought, at zero upstream calls. Editing any step invalidates automatically; misses are never cached, so "nobody had it yesterday" doesn't stop you asking today.
  • Runs tab — per-provider hit rate, share of answers, and cost per answer. Don't compare hit rates between steps: a later step only sees what everything before it missed.
  • Rate limit — per endpoint key, per minute (Settings). It's a spend control: every run buys upstream calls.

3 · Build the JSON with an LLM

The whole waterfall is one JSON document, and /docs/llm.txt is a complete, self-contained specification of it — schema, template language, all 18 condition operators, execution semantics, hard limits, worked examples up to multi-stage parallel definitions, and a checklist of the mistakes models actually make. Every example in it is validated against the real saving route in CI-style checks, so what the spec teaches is what the app accepts.

  1. Create your providers first (section 1). Steps refer to providers by id, so they must exist.
  2. Open a capable LLM. Paste in: llm.txt, the API docs of each provider you want to chain, and what you want (the spec ends with a ready-made prompt template).
  3. Take the JSON it produces, open your endpoint's Build tab → JSON view, paste, and click Apply to builder. Every problem is listed with its exact location — paste the list back into the LLM if anything fails.
  4. Assign each step's provider in the visual view (the model can't know your provider ids — it leaves placeholders, and the JSON view flags them).
  5. Run test, then Save.
Never give an LLM your API keys. It doesn't need them — keys live in the provider's pool and are injected automatically. The spec instructs models to refuse to place auth in steps; the validator rejects it anyway.

4 · Run API

POST https://<your-keyproxy>/api/run/<slug>
x-endpoint-key: kp_ep_...        # or: Authorization: Bearer kp_ep_...
Content-Type: application/json

{ "domain": "acme.com", "first_name": "Ana" }

One JSON object of declared inputs per request (max 128 KB). Response:

{
  "status": "success",                  // success | partial | miss | error
  "output": { "email": "ana@acme.com" },// your normalized fields
  "raw": { ... },                       // the winning provider's response, untouched
  "resolved_by": "hunter",              // which step answered
  "missing": [],                        // required fields still empty
  "error": null,
  "meta": { "duration_ms": 1840, "upstream_calls": 2,
            "cost_cents": 17, "cache_hit": false, "run_id": "..." },
  "trace": [ ...one entry per step: ran/skipped/why, status, latency... ]
}
statusMeaningHTTP
successA provider answered; every required field is filled200
partialSome fields found, but not all required ones200
missEveryone replied; nobody had it200
errorSomething broke — unreachable provider, out of time502
A miss is HTTP 200, not 404. Clay, n8n, Make and Zapier treat any non-2xx as a failure and will retry the row or halt the table — so "no email found" is a successful response that says so. Branch on the status field, never on the HTTP code.

Other responses: 401 bad/missing key · 400 invalid input (with per-field details) · 413 body too large · 429 rate limited (with Retry-After) · 503 endpoint turned off · 409 endpoint has no steps.
