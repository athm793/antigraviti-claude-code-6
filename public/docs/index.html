1 · Concepts

  • Provider — one upstream API plus a pool of API keys. KeyProxy injects the next active key into every call and rotates automatically when one is rate-limited. Providers work standalone (as a pass-through proxy) and as the building blocks of waterfalls.
  • Endpoint — one public URL (/api/run/<slug>) that runs an ordered list of steps. Each step calls one provider; rules decide whether a step runs and whether its response counts as an answer.
  • Definition — the JSON document describing an endpoint's inputs, steps and settings. Every save is an immutable version; the run log records which version each run used, and the cache invalidates automatically when the version changes.
  • The flagship pattern — try Prospeo; if it returns no email, try BetterEnrich, then Hunter. One URL, one response shape whichever provider answers, and per-provider hit rates telling you which vendor earns its keep.

2 · Providers & the proxy

Creating a provider

FieldWhat to enter
Target base URLThe API's origin, e.g. https://api.hunter.io. Must be publicly reachable — localhost, private ranges (RFC1918, link-local, CGNAT), .internal hosts and credentials-in-URL are refused, both at save time and again at request time.
Auth header name + prefixHow this API expects its key: Authorization + Bearer , or X-Api-Key with an empty prefix, etc. Check the provider's own docs — this is the single thing you must get right, because every proxied call and every waterfall step authenticates through it.
Rate-limit status codesWhich responses mean "this key is spent" — usually just 429. Only 400–599 are accepted (a success code here would make the proxy retry its own successes).
Cooldown (minutes)How long a rate-limited key rests before being retried automatically. 0 = benched until you press "Reset all keys".

Then paste your API keys on the provider page, one per line. Keys never leave the server; the dashboard only ever shows a ••••1234 preview.

Calling the proxy

# Before — direct, one key, dies on rate limits
curl "https://api.hunter.io/v2/email-finder?domain=acme.com" \
  -H "X-Api-Key: real-key"

# After — through KeyProxy, rotates across the whole pool
curl "https://<your-keyproxy>/api/proxy/<CONFIG_ID>/v2/email-finder?domain=acme.com" \
  -H "x-master-key: <MASTER_KEY>"

The master key (on the provider card) authenticates you to KeyProxy — it can also be sent as Authorization: Bearer …. KeyProxy strips it, injects the next pool key as the provider's auth header, and forwards everything else — method, path, query, headers, body — unchanged. The upstream response streams back verbatim.

How rotation behaves

  • Keys are used lowest-numbered-first: the pool drains in order rather than spreading load. Under heavy concurrency several requests can land on the same key at once.
  • A response matching the provider's rate-limit codes benches that key (cooldown or exhausted) and the next key is tried immediately, within the same request.
  • Every attempt has its own timeout (default 30 s, tunable via the PROXY_ATTEMPT_TIMEOUT_MS env var), so a hanging upstream fails fast instead of eating the whole function budget.
  • Redirects are not followed — a 3xx comes back to you as-is. Following a Location the upstream chose would send a live key somewhere you never configured.
  • "Rotate" on the provider card mints a new master key (the old one stops working immediately). "Reset all keys" returns every benched pool key to active.

Proxy error responses

When the response comes from KeyProxy itself rather than the upstream, the JSON body carries "proxy": true so you can tell them apart:

HTTPMeaning
503No active keys in the pool, or every key rate-limited during rotation.
504The upstream didn't answer within the per-attempt timeout.
502The upstream couldn't be reached at all.
400The resolved target was blocked (e.g. the URL escaped the provider's base, or resolved to a private address).
401Missing or wrong master key.

3 · Building a waterfall

  1. Endpoints → New endpoint. Pick a name and URL slug (2–60 chars, lowercase letters, numbers, hyphens). You get the public URL and an endpoint key — shown once, then stored only as a hash.
  2. Declare inputs on the Build tab — the fields callers will send. Each becomes a {{input.…}} token usable in any step. Give every input an example: it prefills the test runner.
  3. Add a step per provider, in the order you want them tried. Each step card has five sections:
    • When should this step run? — a condition; empty means always. From step 2 onward you can also toggle "run at the same time as the step above" to form a parallel group.
    • Request — method, path (relative to the provider's base URL), query parameters, extra headers, and body. Type {{ in any field for autocomplete over everything available at that step's position.
    • What counts as an answer? — empty means the default: HTTP 2xx and every required output filled. Add conditions to demand more (e.g. score ≥ 70).
    • Output fields — pull values out of the response into your normalized result, with optional transforms.
    • Then what? — stop on success (waterfall) or carry on (chain); and what a failure does: try the next step, stop, or fail the whole run.
  4. Run test — executes the unsaved draft against your real providers. Live calls, real credits, nothing logged (so experiments never skew your hit rates). Every step row opens to show the exact URL called, the condition traces ("Should it run?" / "Did it answer?"), unresolved placeholders, and the response.
  5. Save waterfall. Saving is versioned and uses an optimistic lock — if someone else saved meanwhile you get a conflict, never a silent overwrite. Settings → Version history lists every save with one-click restore (restore copies the old version forward; history is never rewritten).

Prefer JSON? The Build tab's JSON view shows the whole definition; edits there apply to the builder only when you press Apply, and every validation problem is listed with its exact location. Import/Download round-trips definitions as files. This is also the workflow for LLM-generated definitions.

4 · Definition reference

The definition is one JSON document:

{
  "version": 1,
  "inputs":  [ ... ],      // what callers send            (max 30)
  "steps":   [ ... ],      // ordered steps                (max 12)
  "outputs": [ ... ],      // declared result fields
  "settings": { ... }
}

Inputs

{ "name": "domain", "type": "string", "required": true,
  "example": "acme.com", "description": "Company domain" }
  • type: string · number · boolean · object · array. Caller values are coerced sensibly — "50" → 50 for a number, "true"/"1"/"yes" → true for a boolean. Uncoercible or missing-required values reject the run with HTTP 400 before any provider is called.
  • Undeclared fields a caller sends never reach the templates — declare everything you use.

Step fields

FieldRules
keyStable reference name: ^[a-z][a-z0-9_]{0,39}$, unique. Later steps reference it ({{steps.hunter.output.email}}) — never by position, so reordering can't break references. Renaming a key in the visual editor rewrites every reference automatically.
nameHuman label, required.
config_idThe provider's id. Must be a provider you can access — checked at save and at test.
groupnull, or a shared string on consecutive steps to run them in parallel (§7). A group interrupted by an ungrouped step is invalid.
enabledfalse skips the step but keeps it in the definition.
request.methodGET · POST · PUT · PATCH · DELETE
request.pathRelative to the provider's base URL, starts with /. Templates allowed. Each resolved segment is URL-encoded individually; ./.. segments fail; a missing value in a path fails the step before any billed call.
request.query{key, value} pairs, max 30. A value whose template resolves to nothing drops the parameter entirely — ?email= and no email mean different things to most APIs.
request.headers{key, value} pairs, max 30. Forbidden: host, connection, content-length, transfer-encoding, x-master-key, x-endpoint-key, and the provider's auth header — that one is injected from the key pool. A value resolving to text with a line break fails the step (header forgery).
request.body_typenone · json · raw
request.bodyFor json: a real object, never a string of JSON — values are substituted structurally, not spliced into text, which is what makes caller input unable to inject fields. Templates work in nested values and keys; anything resolving to nothing is dropped. Content-Type: application/json is set automatically. For raw: a template string — set your own Content-Type header.
run_conditionnull = always run. Evaluated before the call, so it sees input.*, result.* and earlier steps — not this step's response. The idiom "only pay for this provider if we still have no email" is result.email is empty.
success_conditionnull = the default: HTTP 2xx and every required_outputs field non-empty after this step's mapping ran. That default is the heart of the product — a provider returning 200 {"email": null} has not answered, and without it the waterfall would stop there.
output_mapMax 40 entries of {field, from, transform}. Runs before the success condition, so conditions can reference output.email. from may be a template or a plain literal (e.g. stamp "prospeo" into a source field).
on_success"stop" — this answer wins, later steps are skipped (waterfall). "continue" — keep going (chain).
on_failure"continue" (try the next step), "stop" (return what's gathered), "fail" (fail the whole run, HTTP 502).
timeout_msnull (default 20000) or 500–45000.
max_key_attemptsnull (default 3) or 1–5 — how many pool keys to try if rate-limited. Every attempt is a real, billed call.
cost_per_call_centsOptional. Feeds cost-per-answer analytics and the parallel-group cost estimate.

Transforms

TransformEffect
noneValue as extracted.
trim / lower / upperString cleanup.
numberParse; unparseable → the field is omitted (never NaN).
booleantrue/1/yes/y → true, false/0/no/n → false, anything else → omitted.
firstFirst element of a list.
joinList → "a, b, c".

Two rules that shape everything: a value resolving to null/nothing never fills a field (so the waterfall can continue past it), while 0 and false do — they are real answers. And once a field is filled, later steps cannot overwrite it: first write wins, empty never overwrites filled.

Settings

KeyMeaning
required_outputsThe fields that make a run count as answered. Drives the default success condition of every step and the run's final status. Usually the single most important setting.
cache_key_fieldsnull = all inputs participate in the cache key, or an array naming which do.
cache_key_excludeInputs excluded from the key (e.g. a trace_id).
cache_key_normalizeDefault true: strings are trimmed + lowercased for caching, so " Acme.com" and "acme.com" share an answer.
group_mergePer parallel group id: first_success (default) · fill_empty · collect — see §7.
max_parallel1–8, concurrency cap inside a group.

5 · Templates

{{root.path}} — a path, nothing else: no expressions, functions, filters or arithmetic. Path syntax: a.b, a.b[0].c, a["key.with.dots"], negative indexes (items[-1] = last). Max 12 segments.

RootMeaningAvailable in
input.<name>A declared caller inputeverywhere
steps.<key>.output.<field>A field an earlier step mappedeverywhere
steps.<key>.body.<path>An earlier step's raw response bodyeverywhere
steps.<key>.statusAn earlier step's HTTP statuseverywhere
result.<field>The merged result so fareverywhere
response.body.<path> / response.statusThis step's responseoutput_map.from and success conditions only
run.id / run.started_atRun id / ISO start timeeverywhere
  • Type preservation: a template that is exactly one placeholder keeps the value's type — {"limit": "{{input.limit}}"} produces {"limit": 50}, not "50". Surrounding text turns it into a string.
  • Reference rules (enforced at save): only earlier steps, never itself (use response.*), never a sibling in its own parallel group. Referencing an undeclared input is a warning.

6 · Conditions

A condition is a JSON tree — {"all": [...]}, {"any": [...]}, {"not": ...}, or a leaf {"path", "op", "value"?}. Trees nest (the visual editor authors one level; nested trees still run and are editable as JSON). Max 200 nodes.

Leaf paths are bare (no braces). In a run condition: input.*, result.*, steps.<key>.*. In a success condition, additionally: status, body.<path>, output.<field>, headers.<name> (case-insensitive), latency_ms.

OperatorsNotes
exists · not_exists · empty · not_empty · is_true · is_falseUnary — no value. empty = missing, null, "", [] or {}. 0 and false are NOT empty — a confidence of 0 is a real answer.
eq · neqLoose: "200" equals 200; booleans match their string forms; objects compare structurally, key-order-independent.
gt · gte · lt · lteNumeric; non-numeric values are simply false, never an error.
contains · not_containsString → substring; array → membership; object → has key.
starts_with · ends_withString prefixes/suffixes.
in · not_invalue must be an array.

There is deliberately no regex operator — compose the string operators instead. Every evaluation produces a full trace (visible in test runs and the run log), so "why was this step skipped?" is always answerable.

7 · How a run executes

  1. Steps run top to bottom. Disabled steps and steps whose run condition fails are skipped — a skipped step costs nothing.
  2. The request is built. A missing value in the path fails the step before any billed call; missing query/header/body values are simply omitted.
  3. The call goes out through the provider's key pool with automatic rotation (up to max_key_attempts).
  4. The output map runs, then the success condition. Success + stop → later steps are skipped and this step's body becomes the response's raw. Success + continue → keep going. Failure → on_failure decides.

Parallel groups

Consecutive steps sharing a group start together (run conditions are checked just before the group starts, against what the run has found so far). Results always merge in declared order, never completion order — the same inputs always produce the same output regardless of which provider replied faster.

  • first_success — the first listed member that answered wins. You still pay every member, every time: the trade is latency for cost, and the builder says so on the group.
  • fill_empty — every member contributes; earlier-listed members win conflicts.
  • collect — every member's values are gathered into arrays.

If nobody in the group answers, the strictest on_failure among members applies (fail beats stop beats continue).

Run status

statusMeaningHTTP
successA step answered and every required field is filled200
partialSome fields found, but not all required ones200
missEveryone replied; nobody had it200
errorSomething broke — unreachable provider, out of time, a fail step failed502
A miss is HTTP 200, not 404. Clay, n8n, Make and Zapier treat any non-2xx as a failure and will retry the row or halt the table — so "no email found" is a successful response that says so. Branch on the status field, never on the HTTP code.

Whole-run budget: 50 seconds, enforced by KeyProxy itself so a timed-out run still returns a complete result and a complete log. Nothing new starts once the clock runs out.

8 · Run API

POST https://<your-keyproxy>/api/run/<slug>
x-endpoint-key: kp_ep_...        # or: Authorization: Bearer kp_ep_...
Content-Type: application/json

{ "domain": "acme.com", "first_name": "Ana" }

One JSON object of declared inputs per request — never an array (one run per request) — max 128 KB. The URL segment accepts the slug or the endpoint id.

9 · Caching

Off by default; enable per endpoint in Settings. The point is money, not latency: a repeated lookup returns the answer you already bought, at zero upstream calls.

  • The cache key is a hash of owner + endpoint + definition version + canonicalized input. Version in the key is the invalidation story: edit a step and every answer bought under the old definition goes cold on its own — nothing to remember to purge. Owner in the key means one account's enriched contact can never be served to another.
  • Input canonicalization is key-order-independent; with cache_key_normalize (default on) strings are trimmed and lowercased. Use cache_key_fields / cache_key_exclude to keep flags like trace_id from fragmenting the cache.
  • Only success and partial results are cached. A miss is not — vendors keep adding data, and "nobody had it yesterday" shouldn't stop you asking today. An error is not — it's transient.
  • TTL is per endpoint (up to 30 days). Settings → "Cached answers" shows the live count and has a manual purge for the one case versioning can't cover: the provider's data changed and your definition didn't.
  • Cache hits appear in the response as meta.cache_hit: true with upstream_calls: 0, and in the run log as "Cached".

10 · Runs, analytics & retention

The Runs tab records every call: when, the input, who answered, calls made, duration, result — every column sortable, filterable by outcome. Each run opens to the full per-step story including condition traces.

Which provider is earning its keep

  • Hit rate — of the runs where a step actually ran, how often it answered. Use it to watch one provider over time.
  • Share of answers — of all runs that got an answer, how often it was this step. This is the "what would I lose by dropping it" number.
  • Cost per answer — total spend ÷ answers, the number that decides whether a vendor stays.
Don't compare hit rates between steps. A later step in a waterfall only ever sees the cases everything before it missed — it is being marked on a harder paper. The dashboard says this too.

What gets stored, and for how long

  • Runs are logged by allowlist: ids, statuses, timings, counts, condition traces, and the caller's input (so a row is recognisable). The result is stored only if you turn on "Save request and response bodies" — it's the personal data your waterfall found, so keeping it is opt-in.
  • Test runs from the Build tab are never logged.
  • Retention is per endpoint (default 30 days, max 365), enforced by a nightly cleanup. Expired cache rows are pruned with it.

11 · Endpoint keys & rate limits

  • Keys look like kp_ep_<id>_<secret>, are shown once at creation, and are stored only as a one-way hash — a database snapshot hands nobody a working key. Issue as many as you need (one per tool is good practice); revoking one doesn't touch the others, so rotation has a grace window.
  • A key is bound to its endpoint — a key for endpoint A can never run endpoint B.
  • The per-minute limit is counted per key, server-side, shared across all instances. It's a spend control: every run buys real upstream calls. 429 responses carry Retry-After.

12 · Building with an LLM

The whole waterfall is one JSON document, and /docs/llm.txt is a complete, self-contained specification of it, written for machine consumption: the same schema, template language, operators, semantics and limits as sections 4–7 above, plus three worked examples up to a parallel-race definition, a checklist of the ten mistakes models actually make, and a ready-made prompt template. Every definition example in it is machine-validated against the real save route, so what the spec teaches is what the app accepts.

  1. Create your providers first (§2) — steps refer to providers by id, so they must exist.
  2. Paste into any capable LLM: llm.txt, the API docs of each provider you want to chain, and what you want (the prompt template is at the end of the spec).
  3. Open your endpoint's Build tab → JSON view, paste the model's output, press Apply to builder. Every problem is listed with its exact location — paste the list back into the LLM if anything fails.
  4. Assign each step's provider in the visual view (the model can't know your provider ids — it leaves placeholders, and the JSON view flags them with the step names).
  5. Run test, then Save.
Never give an LLM your API keys. It doesn't need them — keys live in the provider's pool and are injected automatically. The spec instructs models never to place auth in steps, and the validator rejects it anyway.

13 · Worked example — three-provider email waterfall

Try Prospeo; if it has no email, BetterEnrich; then Hunter, whose answer only counts at score ≥ 70. This exact JSON is validated against the app's save route (it is example A in llm.txt — two more, a chain and a parallel-race, live there).

{
  "version": 1,
  "inputs": [
    { "name": "first_name", "type": "string", "required": true,  "example": "Ana" },
    { "name": "last_name",  "type": "string", "required": true,  "example": "Garcia" },
    { "name": "domain",     "type": "string", "required": true,  "example": "acme.com" }
  ],
  "steps": [
    { "key": "prospeo", "name": "Prospeo",
      "config_id": "REPLACE_WITH_PROVIDER_ID_PROSPEO",
      "group": null, "enabled": true,
      "request": { "method": "POST", "path": "/email-finder",
        "query": [], "headers": [], "body_type": "json",
        "body": { "first_name": "{{input.first_name}}",
                  "last_name":  "{{input.last_name}}",
                  "company":    "{{input.domain}}" } },
      "run_condition": null, "success_condition": null,
      "output_map": [
        { "field": "email",  "from": "{{response.body.response.email}}", "transform": "lower" },
        { "field": "source", "from": "prospeo", "transform": "none" }
      ],
      "on_success": "stop", "on_failure": "continue",
      "timeout_ms": null, "max_key_attempts": null, "cost_per_call_cents": 2 },
    { "key": "betterenrich", "name": "BetterEnrich",
      "config_id": "REPLACE_WITH_PROVIDER_ID_BETTERENRICH",
      "group": null, "enabled": true,
      "request": { "method": "POST", "path": "/api/find-work-email",
        "query": [], "headers": [], "body_type": "json",
        "body": { "full_name": "{{input.first_name}} {{input.last_name}}",
                  "domain": "{{input.domain}}" } },
      "run_condition": null, "success_condition": null,
      "output_map": [
        { "field": "email", "from": "{{response.body.email}}", "transform": "lower" }
      ],
      "on_success": "stop", "on_failure": "continue",
      "timeout_ms": null, "max_key_attempts": null, "cost_per_call_cents": 5 },
    { "key": "hunter", "name": "Hunter",
      "config_id": "REPLACE_WITH_PROVIDER_ID_HUNTER",
      "group": null, "enabled": true,
      "request": { "method": "GET", "path": "/v2/email-finder",
        "query": [
          { "key": "domain",     "value": "{{input.domain}}" },
          { "key": "first_name", "value": "{{input.first_name}}" },
          { "key": "last_name",  "value": "{{input.last_name}}" }
        ],
        "headers": [], "body_type": "none", "body": null },
      "run_condition": null,
      "success_condition": { "all": [
        { "path": "status", "op": "eq", "value": 200 },
        { "path": "output.email", "op": "not_empty" },
        { "path": "body.data.score", "op": "gte", "value": 70 }
      ] },
      "output_map": [
        { "field": "email",      "from": "{{response.body.data.email}}", "transform": "lower" },
        { "field": "confidence", "from": "{{response.body.data.score}}", "transform": "number" }
      ],
      "on_success": "stop", "on_failure": "continue",
      "timeout_ms": null, "max_key_attempts": null, "cost_per_call_cents": 12 }
  ],
  "outputs": [
    { "field": "email", "description": "Verified work email" },
    { "field": "confidence" },
    { "field": "source" }
  ],
  "settings": {
    "required_outputs": ["email"],
    "cache_key_fields": null, "cache_key_exclude": [],
    "cache_key_normalize": true, "group_merge": {}, "max_parallel": 5
  }
}

Why it works: required_outputs: ["email"] makes the default success rule "2xx AND email non-empty", so Prospeo returning 200 {"email": null} counts as a miss and the run falls through. Hunter layers a custom rule on top: its answer only counts at score ≥ 70. Each step stamps or maps only what it can vouch for, and first-write-wins merging keeps earlier answers intact.

14 · Limits & troubleshooting

Hard limits

steps ≤ 12 · inputs ≤ 30 · query params ≤ 30/step · headers ≤ 30/step · output_map ≤ 40/step · rule nodes ≤ 200/condition · max_parallel 1–8 · timeout_ms 500–45000 · max_key_attempts 1–5 · run body ≤ 128 KB · whole-run budget 50 s.

Common problems

SymptomCause / fix
"Someone else saved changes…" on saveThe optimistic lock: another tab/person saved first. Reload, redo, save.
A field comes back empty though the provider had itOpen the run (or test run) and check unresolved — the mapping path doesn't match the real response shape. Fix the from path.
Waterfall stops at a provider that returned nothingrequired_outputs is empty, so any 2xx counts as an answer. Set it.
Step shows "Provider gone"Its provider was deleted. Pick a new one in the step's Provider dropdown. (Deleting a provider that live endpoints use is blocked with the list of them.)
"…uses providers that aren't available to you"The definition names provider ids from another account or that no longer exist — reassign in the visual editor.
Automation treats a miss as failureIt's branching on HTTP code. A miss is 200 — branch on the status field.
429 on runsThat key's per-minute limit (Settings). Raise it, or issue separate keys per tool.
