The one decision everything hangs off

A waterfall definition is one JSONB blob on an immutable version row, not a steps table. Because the Neon HTTP driver can't do interactive transactions, a multi-row save can't be atomic — and a half-saved waterfall doesn't just look wrong, it runs and spends money. One JSONB write is atomic by definition. It also gives:

  • Optimistic locking — UPDATE … WHERE revision = $expected; the loser gets a 409, not a silent overwrite.
  • The execution snapshot a run log needs — a run references the exact version it ran.
  • Cache invalidation for free — the version id is part of the cache key.
  • Restore as append — restoring copies an old version forward as a new one; history is never rewritten.

Cost: no FK from steps to proxy_configs. Covered by save-time ownership checks (endpointGuards.ts), a config_missing step outcome at run time, and a delete guard (endpointsUsingConfig) that refuses to delete a referenced provider.

Layering

src/lib/engine/*      pure functions, zero I/O   ← 134 tests run against this
src/lib/runner.ts     server adapter: providers, rotation, scrubbing
src/lib/rotation.ts   the key-rotation loop (shared by proxy + waterfalls)
src/app/api/run/…     the public endpoint: auth → rate limit → run → after() log+cache

The engine takes its I/O as injected deps. That's what makes the expensive behaviour provable without credits: tests assert which providers were not called.

Schema creation

initSchema() runs on cold start, cached per instance. The endpoint DDL is one batched transaction behind pg_advisory_xact_lock — CREATE TABLE IF NOT EXISTS races on concurrent cold starts. Post-hoc columns use ADD COLUMN IF NOT EXISTS; the credits_used → upstream_calls rename is guarded with a DO $$ block since RENAME COLUMN has no IF EXISTS.
