Waterfall engine

All of src/lib/engine/ is pure — no sockets, no DB, no logs. 151 checks in tests/engine.test.mjs run against the compiled output (npm test), zero credits.

Templates (template.ts, paths.ts)

  • Placeholders name paths, nothing else: {{input.domain}}, {{steps.prospeo.output.email}}. No eval, no expression language.
  • Roots are a closed list — input, steps, response, result, run. No env/process, so no template can reach a secret.
  • A template that is exactly one placeholder keeps the resolved value's type: {"limit":"{{input.limit}}"} → {"limit":50}, not "50".
  • JSON bodies are built by walking the stored object and stringifying once at the end — never splicing into a JSON string, which breaks on the first quote and lets a caller inject fields into an authenticated request.
  • __proto__/constructor/prototype blocked on read and write; contexts are null-prototype. The write side is the one that matters — assigning through __proto__ would pollute the warm instance for other callers.
  • result.* reads what the run has merged so far — "only call this vendor if we still have no email" without naming every earlier step.

Conditions (rules.ts)

  • JSON trees (all / any / not / leaf), 18 operators, deliberately no regex (no V8 regex timeout; subjects come from upstream).
  • empty means missing / null / "" / [] / {} — 0 and false are NOT empty; a confidence of 0 is a real answer.
  • The evaluator returns a full trace, never just a bool, and doesn't short-circuit — "why was this step skipped?" is always answerable.
  • Default success rule = 2xx AND every required output non-empty. This is what the feature rests on: a 200 with {"email": null} has not resolved anything and must fall through.

Requests (request.ts)

  • Path segments resolved and encoded individually; ./.. rejected; a missing path value fails the step before any billed call.
  • Query via URLSearchParams; a missing value drops the parameter entirely (?email= and no email mean different things).
  • Headers: reserved names and the provider's auth header rejected; a resolved value containing CR/LF rejected (header forgery).

Executor (execute.ts)

  • Steps are grouped into stages — one ungrouped step, or a run of consecutive steps sharing a group.
  • A grouped stage runs its members concurrently (worker pool, capped by max_parallel), but results merge in declared order, never completion order — same inputs must give same outputs. There's a test where the second member finishes first and the first still wins.
  • Merge modes per group: first_success (first hit in listed order), fill_empty, collect. When nobody answers, the strictest on_failure among members decides: fail > stop > continue.
  • mergeOutput: first write wins, empty never overwrites — a later gap-filler can't blank out what an earlier provider found.
  • Deadline checked once per stage (starting half a group wastes money); nothing starts with <1s left; a run resolves before the deadline still returns success.
  • Run statuses: success / partial / miss / error. A miss is HTTP 200 — Clay, n8n, Make, Zapier treat non-2xx as failure and retry or halt the row. Only genuine breakage is a 502.

Validation (validate.ts)

One validator shared by the builder (every keystroke), the JSON view, the save route, and the test route — if they disagreed you'd get definitions that save but won't run. Rejects duplicate step keys, forward references, same-group sibling references, self-references, string JSON bodies, unknown operators, non-contiguous groups. Caps in LIMITS (12 steps, 5 key attempts/step, 8 parallel…) are the spend-control backstop. Unknown top-level keys are preserved in _extra, not stripped.

Server adapter (runner.ts)

  • Loads each distinct provider once; cooldown recovery once per provider per run; burned keys shared across steps on the same pool.
  • verifyTarget: true per step — DNS re-resolved immediately before the fetch, because it can be repointed after the provider was saved.
  • Response bodies read streamed with a 2MB cap; 3xx refused; hard 50s deadline against Vercel's 60s so a timeout still produces a complete log.
  • Every key value in play is scrubbed from the result before it can reach a response or log (redact.ts — safety net, not guarantee; ownership is the structural control).
